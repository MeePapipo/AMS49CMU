## หลักสามข้อที่โครงสร้างทั้งหมดวางอยู่บนนี้

**1 · ยอดเงินคำนวณที่เซิร์ฟเวอร์เท่านั้น**
หน้าเว็บส่ง "จำนวนเสื้อรายไซส์ + ยอดบริจาค" ขึ้นไป เซิร์ฟเวอร์คิดยอดเองแล้วส่งกลับมา
เลขที่แสดงบนขั้น "โอนยอดรวม" คือเลขจากเซิร์ฟเวอร์ ไม่ใช่เลขคณิตในเบราว์เซอร์

ต้นแบบเคยเจอของจริงมาแล้ว: เบราว์เซอร์แคช `app.js` ตัวเก่าไว้ ยอดรวมบนหน้าจอค้างไม่ขยับ
แต่ช่องจำนวนยังกดเพิ่มได้ ผู้ใช้จึงโอนตามยอดที่ผิดโดยไม่รู้ตัว ต้นแบบแก้ด้วยการเทียบเลข
เวอร์ชันไฟล์แล้วหยุดทั้งหน้า ซึ่งเป็นการกันอาการ — ที่นี่แก้ที่ต้นเหตุ
ตอนกดส่ง ไคลเอนต์แนบยอดที่ตัวเองแสดงอยู่ไปด้วย (`clientTotal`) เซิร์ฟเวอร์คิดใหม่แล้วเทียบ
ไม่ตรง = ไม่บันทึก แล้วบอกให้โหลดหน้าใหม่

**2 · ข้อมูลไหนออกไปถึงใคร ตัดสินที่เดียว**
`functions/lib/shape.ts` มีสามฟังก์ชัน — `toPublicLedger` (หน้าแรก) · `toStatusView` (หน้าเช็คสถานะ)
· `toAdminView` (หลังบ้าน) ทุก endpoint เลือกฟิลด์ผ่านสามอันนี้ ไม่มีที่ไหน `SELECT *`
แล้วส่งทั้งแถวออกไป เพิ่มคอลัมน์ใหม่ในตารางเมื่อไร จึงไม่หลุดออกหน้าสาธารณะโดยอัตโนมัติ

**3 · สิทธิ์ตัดสินที่เซิร์ฟเวอร์ ไม่ใช่ที่เบราว์เซอร์**
`functions/api/admin/_middleware.ts` เป็นด่านเดียวของทุกอย่างใต้ `/api/admin/*`
การซ่อน/แสดงส่วนต่าง ๆ ใน `admin.html` ไม่ใช่การป้องกัน — ต่อให้แก้ DOM ให้คอนโซลโผล่มา
ทุก endpoint ก็ยังตอบ 401
(ต้นแบบเทียบรหัส `admin`/`Admin001` ด้วย JavaScript ในหน้าเว็บ ซึ่งกด Ctrl+U ก็อ่านได้)

`assets/system.css` ยกมาจากต้นแบบทั้งไฟล์ ไม่ได้แก้อะไร
`assets/app.js` ยกครึ่งล่างมาทั้งหมด (ตัวนับไซส์ formatter badge clipboard validation)
ส่วนครึ่งบนที่เคยอ่านเขียน `localStorage` ถูกแทนด้วยตัวเรียก API

**เว็บนี้ไม่เขียนอะไรลง `localStorage` เลยแม้แต่อย่างเดียว**
ต้นแบบเก็บ "ร่างฟอร์มที่กรอกค้างไว้" เพื่อให้ปิดหน้าไปเปิดแอปธนาคารแล้วกลับมาต่อได้
ฟีเจอร์นั้นถูกถอดออกตามที่ผู้จัดงานสั่ง (5 ส.ค. 2569) — ปิดแท็บหรือรีเฟรชระหว่างกรอก
ข้อมูลจะหายหมด จึงชดเชยด้วยการเตือนก่อนออกจากหน้า (`beforeunload` ท้าย `page-support.js`)
และแก้ข้อความในขั้น "โอนยอดรวม" ให้บอกตรง ๆ ว่าอย่าปิดหน้านี้
ถ้าจะเอากลับมา ต้องเอากลับทั้งชุด (บันทึก + กู้ + แบนเนอร์ + ปุ่มเริ่มใหม่) —
กู้เงียบ ๆ โดยไม่มีแบนเนอร์จะแย่กว่าไม่มีเลย เพราะผู้ใช้จะเจอฟอร์มที่มีข้อมูลเก่าโดยไม่รู้ที่มา

**สคริปต์ของแต่ละหน้าอยู่ในไฟล์แยก ไม่ใช่ `<script>` inline เหมือนต้นแบบ**
เพราะแบบนั้นทำให้ตั้ง `script-src 'self'` ใน CSP ไม่ได้

## ตัดสินใจอะไรไว้บ้าง และทำไม

### รหัสอ้างอิงยาว 6 ตัว ไม่ใช่ 4 ตัวเหมือนต้นแบบ

4 ตัวจากชุด 32 ตัวอักษร = 1,048,576 ค่า พอตอนข้อมูลอยู่ใน `localStorage` เพราะไม่มี API ให้ยิง
แต่พอมี `GET /api/status/:ref` ของจริง สคริปต์ตัวเดียวไล่ครบทั้งชุดได้ในไม่กี่ชั่วโมง
แล้วดูดยอด ไซส์ จังหวัดและไปรษณีย์ของทุกคน — ซึ่งทำลายหลักการของเว็บนี้ตรง ๆ
(โปร่งใสได้เพราะไม่มีใครสืบย้อนว่าเงินก้อนไหนของใคร)

6 ตัว = 1,073,741,824 ค่า + จำกัด 20 ครั้ง/นาที/IP = ยิงไม่ไหว
ชุดตัวอักษรยังตัด `I O 0 1` ออกเหมือนเดิม และเมื่อผู้ใช้พิมพ์ตัวเหล่านั้นมา ระบบจะบอกว่า
"รหัสไม่มีตัวนี้เลย ลองดูว่าเป็น J หรือ L หรือเปล่า" — **แต่ไม่ดัดให้เอง**
เพราะเดาผิดหนึ่งตัวหมายถึงเปิดรายการของคนอื่นให้ดู ซึ่งแย่กว่าการบอกว่าไม่เจอ

### เก็บยอดที่คำนวณได้ลงฐาน พร้อม `price_version`

ขัดกับกฎ "ห้ามเก็บ `amount` ซ้ำ" ของต้นแบบโดยตั้งใจ
ยอดที่เรียกเก็บไปแล้วคือข้อเท็จจริงทางประวัติศาสตร์ที่ต้องตรงกับ statement ธนาคาร
ถ้าคำนวณสดทุกครั้ง วันที่แก้ตารางราคาแถวเก่าทุกแถวจะเปลี่ยนค่าเงียบ ๆ

กันการ drift ด้วยการเทียบ: หน้าหลังบ้านคิดยอดใหม่จากตารางปัจจุบันทุกครั้งที่แสดง
ถ้าไม่ตรงกับที่เก็บไว้จะขึ้นธงเตือน พร้อมบอกว่า **ให้ยึดยอดที่เก็บไว้** เพราะนั่นคือเงินที่เข้าจริง

### ตรวจไฟล์สลิปจากไบต์ ไม่ใช่จากที่ไคลเอนต์แจ้ง

`sniffType()` อ่าน magic bytes 16 ไบต์แรก ไฟล์ที่เปลี่ยนนามสกุลเป็น `.png` เฉย ๆ ตกด่านนี้
ต้นแบบตรวจ `file.type` ที่เบราว์เซอร์อย่างเดียว ซึ่งข้ามได้ทั้งหมด

### ฟอนต์โฮสต์เอง

ต้นแบบลิงก์ไป `fonts.googleapis.com` ซึ่งส่ง IP ของทุกคนที่เปิดเว็บไปที่ Google
โดยไม่ได้ขออนุญาต ขัดกับข้อความ PDPA ที่เราเขียนไว้ในฟอร์มเอง
เอามาไว้เองแล้ว 232 KB (เฉพาะ latin / latin-ext / thai) และได้ `font-src 'self'` ใน CSP

### กันกดส่งซ้ำ

ต้นแบบตั้งแค่ `data-loading` แต่ไม่ `disabled` ปุ่ม กดรัวระหว่างรอเซิร์ฟเวอร์จึงได้สองรายการ
บนของจริงคือสองแถวในฐานข้อมูลและสองรายการบนบัญชีสาธารณะ

### session แอดมินหมดอายุสามชั้น

ผู้จัดงานพบว่ากรรมการที่ลืมกดออกจากระบบ พอปิดเบราว์เซอร์แล้วเปิดใหม่ยังเข้าคอนโซลได้เลย
สาเหตุคือ cookie เดิมตั้ง `Max-Age=8h` ซึ่งเบราว์เซอร์เขียนลงดิสก์เป็น persistent cookie

แก้เป็นสามชั้นซ้อนกัน เพราะไม่มีชั้นไหนกันได้ครบเอง

| ชั้น | ที่ไหน | กันอะไร |
|---|---|---|
| session cookie (ไม่มี `Max-Age`) | `lib/crypto.ts` → `sessionCookieHeader()` | ปิดเบราว์เซอร์แล้ว cookie หาย |
| อายุสูงสุด 3 ชั่วโมง | `lib/crypto.ts` → `SESSION_TTL_MS` | เพดานแข็ง ตรวจที่เซิร์ฟเวอร์จาก `exp` ที่เซ็นไว้ |
| ไม่ใช้งาน 20 นาที | `page-admin.js` → `IDLE_MS` | **ชั้นที่กันเคสจริงได้** — เครื่องที่เปิดทิ้งไว้แล้วลุกไปทำอย่างอื่น |

ชั้นแรกไม่ได้กันได้ 100% — Chrome/Edge ที่เปิด "เปิดต่อจากที่ค้างไว้" จะกู้ session cookie
กลับมาให้ และเบราว์เซอร์บนมือถือแทบไม่เคยถูกปิดจริง จึงต้องมีชั้นสองกับสาม

ตอนหมดเวลา ระบบ **ล้างตารางกับบันทึกการใช้งานออกจาก DOM ก่อน** แล้วค่อยเรียก logout
เพราะข้อมูลชื่อ เบอร์ และที่อยู่ของทุกคนค้างอยู่ในหน้าจอ ต่อให้ cookie ถูกลบไปแล้วก็ยังอ่านได้จากจอ

**สิ่งที่ตั้งใจไม่ทำ** — ไม่ออกจากระบบตอนสลับแท็บ (`visibilitychange`) เพราะกรรมการต้อง
สลับไปเปิด statement ธนาคารเทียบยอดตลอดเวลา และไม่ยิง logout ตอน `beforeunload`
เพราะเบราว์เซอร์ตัดทิ้งได้ แถมกดรีเฟรชธรรมดาก็จะหลุดทุกครั้ง

### CSV กัน formula injection

ต้นแบบครอบแค่เครื่องหมายคำพูด — พอสำหรับให้ไฟล์ไม่พัง แต่ไม่พอสำหรับความปลอดภัย
ช่องที่ผู้ใช้พิมพ์เอง ถ้าขึ้นต้นด้วย `= + - @` Excel จะรันเป็นสูตรทันทีที่เปิดไฟล์
และคนที่เปิดไฟล์นี้คือกรรมการที่เห็นข้อมูลของทุกคน — ตอนนี้ใส่ `'` นำหน้าให้

## ข้อตัดสินใจที่ห้ามเปลี่ยนโดยไม่ตั้งใจ

ยกมาจากต้นแบบทั้งหมด ยังใช้อยู่

1. **ค้นสถานะด้วยรหัสอ้างอิงเท่านั้น ห้ามใส่ช่องค้นด้วยชื่อ** — รุ่นเดียวคนไม่เยอะ
   ค้นด้วยชื่อเมื่อไรจะเดาออกทันทีว่าใครบริจาคเท่าไร
2. **หน้าเช็คสถานะไม่โชว์ที่อยู่เต็ม** โชว์แค่จังหวัด+ไปรษณีย์ (`toStatusView`)
3. **ไม่เอาภาพถ่ายสมุดบัญชีขึ้นเว็บ** — ไฟล์ต้นฉบับมีลายเซ็นผู้มีอำนาจและตราประทับธนาคาร
4. **ไม่มี QR พร้อมเพย์ และจะไม่มี** — บัญชีร่วมสองชื่อผูกพร้อมเพย์ไม่ได้ ใช้ปุ่มคัดลอกยอดแทน
5. **ยอดที่แจ้ง = ยอดที่ระบบคำนวณ** ผู้ใช้พิมพ์ยอดเองไม่ได้ โอนผิดยอดให้แอดมินตีกลับ
6. **ไม่จำกัดจำนวนเสื้อ** — `SIZE_MAX` (99/ไซส์) และ `BULK_HINT` (10) เป็นตัวกันพิมพ์พลาดและ
   ตัวเตือน ไม่ใช่โควตา
7. **หน้าสาธารณะแสดงได้แค่ เวลา · รหัส · สถานะ · ยอด**
8. **การสะกดชื่อบัญชี** — "ปิ่นปินันท์" และ "ชัชวาลชัยทรัพย์" (ช ไม่ใช่ ซ) ยืนยันโดยผู้จัดงาน
   แม้ตัวอักษรในภาพสมุดบัญชีจะดูเหมือน ซ ก็ตาม อย่าแก้กลับโดยอ้างภาพอย่างเดียว
9. **ตารางไซส์ในภาพ `size-chart.jpg` มีถึง 3XL เท่านั้น** 4XL/5XL เพิ่มมาทีหลัง

## เรื่องที่ต้องรู้ก่อนแก้โค้ด

**`grid-template-columns: 1fr` พังกับข้อความไทย**
`1fr` มีขั้นต่ำเป็น min-content ของสิ่งข้างใน และ `overflow-wrap: break-word` ไม่ได้ลด min-content
ข้อความไทยไม่มีช่องว่าง min-content จึงยาวทั้งประโยค แทร็กโป่งจนทั้งหน้าเลื่อนแนวนอนที่ 320px
→ ใช้ `minmax(0,1fr)` เสมอ **รวมถึงใน media query ที่เขียนทับด้วย**

**`.ledger-admin` อาศัย `data-l="…"` บนแต่ละ `<td>`**
จอแคบซ่อน `<thead>` แล้วเอาค่านั้นมาเป็น label — เพิ่มคอลัมน์ใหม่ต้องใส่ `data-l`
และวาง `grid-row` ใน `system.css` ด้วย

**Workers แผนฟรีจำกัด CPU 10 มิลลิวินาทีต่อคำขอ**
เป็นเหตุผลที่ PBKDF2 ตั้งไว้ 25,000 รอบ ไม่ใช่สองแสน และเป็นเหตุผลที่รหัสผ่านแอดมิน
ต้องเป็นค่าที่สุ่มมา ไม่ใช่คำที่คนคิดเอง (ดู `functions/lib/crypto.ts`)

**เวลาทั้งระบบเป็นสตริง `YYYY-MM-DDTHH:MM` ตามเวลาไทย ไม่มี timezone suffix**
Worker รันที่ UTC เสมอ จึงต้องบวก 7 ชั่วโมงเองผ่าน `thNow()` ห้ามพึ่ง `toLocaleString` ของ runtime

**`npm run smoke` มีเทสต์ที่ "ต้องล้มเหลว" อยู่ครึ่งหนึ่ง**
ยอดที่แก้เอง ไฟล์ปลอม เข้าหลังบ้านโดยไม่ล็อกอิน ยิงรัว ๆ CSRF จากโดเมนอื่น
ถ้าเทสต์พวกนี้เปลี่ยนเป็นผ่าน แปลว่ามีด่านหลุดไป — ไม่ใช่เรื่องดี

## ยังไม่ได้ทำ

- ยอดเป้าหมาย 500,000 บาท เป็นตัวเลขตัวอย่าง ยังไม่ได้รับตัวเลขจริง (`GOAL_AMOUNT` ใน `wrangler.toml`)
- ไม่มีการส่งอีเมล/LINE แจ้งผู้บริจาคเมื่อยอดถูกยืนยัน — ต้องเข้ามาเช็คเองด้วยรหัสอ้างอิง
- การลบข้อมูลตอนปิดโครงการต้องกดทีละรายการ (ปุ่มอยู่ใต้ "ปิดโครงการ · ลบข้อมูลส่วนบุคคล"
  ในกล่องตรวจสลิป) ยังไม่มีปุ่มลบทั้งหมดครั้งเดียว — ถ้าจะลบทีเดียวใช้ SQL ตามที่เขียนไว้ใน DEPLOY.md
- ยังไม่ได้ทดสอบกับ Cloudflare Access ของจริง โค้ดตรวจ JWT ครบแล้วแต่ต้องมีบัญชี Zero Trust
  ถึงจะยืนยันได้ปลายทาง (ดูขั้นตอนที่ 5 ใน DEPLOY.md)
